# Seguridad

- Secretos en gestor de variables de entorno o .env.local ignorado. .env.example solo nombres/placeholders. Clave publicable de Supabase apta para cliente con RLS correcto; service_role y claves secretas nunca cliente ni repositorio.
- RLS por operación y membresía; no confiar en parámetros del cliente. Validar identidad y autorización en servidor y DB. Evitar acceso cruzado, XSS, fugas en logs y errores detallados.
- Cuenta demo limitada, datos sintéticos, sin permisos de infraestructura. Entregar credenciales por canal privado; no ponerlas en README, commits o informes.
- Separar pruebas de producción. No ejecutar resets, migraciones destructivas o pruebas de escritura contra producción sin autorización explícita.
- Revisar diff, historial Git y archivos antes de hacer público el repo; si se expone un secreto, revocarlo/rotarlo primero y tratar el historial.
- No activar facturación, exponer enlaces privados ni ampliar permisos sin autorización humana. Los permisos de herramientas de agentes no son una frontera de seguridad completa.

## Permisos de herramientas de agentes (.claude/settings.json)
Fuente de las reglas: hechos de la documentación oficial de Claude Code aportados por Orchestrator (https://code.claude.com/docs/en/, páginas "permissions" y "sub-agents"); Develop no tuvo acceso a red y no los verificó de forma independiente. La evaluación es deny, luego ask, luego allow: un allow no crea excepciones a un deny.

- Modo manual: `defaultMode` es `default` y `disableBypassPermissionsMode` es `disable`. No hay `allow` amplio ni se usa `--dangerously-skip-permissions`. No se define allowlist explícita: los comandos de solo lectura (`git status`, `git diff`, `git log`, `pnpm lint`) se ejecutan con el flujo de permisos normal y se evita ampliar permisos sin necesidad. Si en el futuro se añade `allow`, solo para comandos de solo lectura y sin banderas de escritura.
- Lectura (deny): `.env`, `.env.local`, `.env.*.local`, `.env.development`, `.env.production`, `.env.test`, `.env.staging`, `.vercel/**`, `secrets/**`, claves y certificados (`*.pem`, `*.key`, `*.p12`, `*.pfx`), `credentials*.json`, `service-account*.json`, `id_rsa*`, `id_ed25519*` y `.claude/settings.local.json`, más credenciales del usuario fuera del repositorio (`~/.ssh`, `~/.aws`, `~/.config/gh`, `~/.git-credentials`, `~/.npmrc`). No se usa el patrón `.env.*` porque bloquearía `.env.example`, que debe seguir legible y un `allow` no puede excepcionar un deny.
- Escritura (deny de Edit): los mismos archivos de entorno, claves y `secrets/**`, sin cubrir `.env.example`.
- Bash y PowerShell, deny (acciones remotas, irreversibles o de despliegue): `git push`, `git merge`, `git reset --hard`, `git clean`, `git remote add|set-url|remove|rename`, `gh pr merge`, `gh repo create|delete|edit|rename|archive`, `gh release`, `gh secret`, `gh variable`, `gh auth token`, `vercel` y `netlify` (también vía `npx` y `pnpm dlx`), `npm|pnpm publish`, borrado recursivo y Supabase remoto, con credenciales o que puede facturar. Se deniega cada comando con y sin argumentos. Un deny equivale a "lo ejecuta el humano".
  - Borrado recursivo en Bash: `rm` con `-r`, `-R` o `--recursive`, sea la primera bandera (`rm -r*` y `rm -R*`: `-rf`, `-rv`, `-rI`, `-rfv`…), esté agrupada con otras en segunda o tercera posición (`-fr`, `-vr`, `-dr`, `-Ir`, `-fvr`, `-ivR`…, con las letras f, v, i, I, d, P y x) o aparezca después de otros argumentos (`rm * -r*`, `rm * -R*`, `rm * --recursive*`). Se usa un comodín final sin espacio (`rm -r*`), que cubre el comando solo, con argumentos y las banderas agrupadas.
  - Borrado en PowerShell: `Remove-Item` con `-Recurse` o `-Force` en primera posición, incluidas las abreviaturas por prefijo `-r*` y `-fo*` (con ambas capitalizaciones, porque la distinción de mayúsculas no está verificada), y sus alias `rm`, `ri`, `del`, `erase`, `rd` y `rmdir` con esas mismas banderas. Según los hechos aportados por Orchestrator, la herramienta canonicaliza los alias a `Remove-Item`, de modo que las reglas de alias son defensa en profundidad por si no se aplicara. También `rd|rmdir|del|erase /s` (forma de cmd) y `Format-Volume`.
  - Supabase remoto, con credenciales o facturable: `db push`, `db pull`, `db reset --linked|--db-url`, `link`, `login`, `functions deploy`, `functions delete`, `secrets`, `projects`, `branches` (las ramas de Supabase pueden facturar), `migration repair`, `migration up --linked|--db-url` y `db dump --linked`.
- Bash y PowerShell, ask (cambian el repositorio o la red, pero son habituales): `git add`, `git commit`, `git checkout`, `git switch`, `git stash`, `git rebase`, `git config`, `git pull`, `git restore`, `git rm`, `git branch -D`, instalación o actualización de dependencias (`pnpm|npm install|add|update`, `pnpm dlx`, `npx`), `curl`, `wget`, `psql`, `pg_dump`, `gh api`, `gh pr create`, `gh workflow`, `gh auth`, `gh issue` y `gh run` (escriben en el remoto o relanzan, cancelan o borran ejecuciones de CI, que consumen minutos; el ask alcanza también a sus subcomandos de lectura, lo que se acepta porque un ask pide confirmación y no bloquea), `Invoke-WebRequest` e `Invoke-RestMethod` (y sus alias `iwr`, `irm`), `Remove-Item` en las formas no denegadas, `supabase db reset` local y `supabase db dump`, y los saltos de shell `powershell`, `pwsh` y `cmd` desde Bash, y `cmd` desde PowerShell (`cmd /c rmdir /s` esquivaría las reglas de borrado). `git add` y `git commit` están en ask: los agentes no commitean sin autorización humana (decisión del Orchestrator en TASK-002, sujeta a revisión humana). `git push` y toda operación remota están en deny.
  - Los ask de `git config` y `git stash` se mantienen amplios y alcanzan también a sus variantes de lectura (`git config --get|--list`, `git stash list|show`). Motivo: la evaluación es deny, ask y luego allow, así que un allow no puede exceptuar un ask; y enumerar solo las variantes de escritura no es fiable, porque `git config <clave> <valor>` escribe sin ninguna bandera y no se distingue por prefijo de `git config <clave>`. Un ask pide confirmación y no bloquea el comando.
  - No se ha verificado que el ask muestre su diálogo cuando lo dispara un subagente (Testing no observó ninguno; Orchestrator no puede ver esos diálogos: docs/reviews/claude/TASK-002-POST.md, POST-03, y TASK-002.md, ORC-07). La prueba quedó cancelada por DH-G1 y sigue sin verificar (AUD-03/RV-02, Medium provisional): DH-10 descansa en el contrato textual, la comprobación Git y la revisión de diff.
- Comandos de desarrollo legítimos no se bloquean: `git status`, `git diff`, `git log`, `git show`, `git ls-files`, `git check-ignore`, `git check-attr`, `git rev-parse`, `git branch --show-current`, `node`, `pnpm lint|typecheck|test|build|dev`, `ls`, `grep`, `cat`.
- Sin hooks de frontmatter en TASK-002 (decisión del Orchestrator): la aplicación por ruta no es técnica; se comprueba por diff.

## MCP y conectores
- `disableClaudeAiConnectors` es `true` en `.claude/settings.json`: desactiva los conectores de la cuenta claude.ai, pero no alcanza a los de las sesiones locales de Desktop (RV-01; véase "Riesgo residual aceptado"). No se registran identificadores de conectores en el repositorio. No existe `.mcp.json` ni se añaden servidores MCP al proyecto.
- No se usa un deny global `mcp__*` en settings (decisión del Orchestrator, DH-12, sujeta a revisión humana). Motivo: observación del Orchestrator (docs/reviews/claude/TASK-002.md, ORC-06) basada en la semántica documentada de `mcp__*` y en los nombres de herramientas de la aplicación de escritorio, que expone herramientas internas con prefijo `mcp__`; un deny global las bloquearía también. No se ha verificado ejecutando ese deny. Se deniega por servidor local de alto riesgo visible en la sesión: `mcp__computer-use__*`, `mcp__claude-in-chrome__*` y `mcp__scheduled-tasks__*`. Las reglas `mcp__` se escriben sin paréntesis, porque con paréntesis se ignoran.
- Develop y Testing llevan `disallowedTools: mcp__*` como defensa en profundidad; su allowlist `tools` ya excluye MCP según la documentación y `mcpServers` solo añade servidores, no bloquea.
- Limitaciones: los servidores MCP de plugins (p. ej. GitHub de un plugin) tienen un nombre de herramienta no verificado; su desactivación efectiva requiere que el humano use los interruptores de conectores (el cambio se guarda en `~/.claude.json`, global, que ningún agente toca) o verifique el prefijo real para añadir una regla. El texto de instrucciones MCP puede seguir apareciendo en el contexto aunque las herramientas no sean invocables. `disableClaudeAiConnectors` no está documentado como recarga en caliente. Comprobaciones y equivalentes de Desktop: docs/AGENT_WORKFLOW.md, sección "Comprobación de agentes, modelos, esfuerzos y permisos".
- Si una fase futura necesita un servidor MCP (p. ej. Supabase en F3), la relajación la decide el humano de forma explícita y se limita a esa fase.

## Límites de las reglas de permisos
Las reglas deny y ask no son una frontera de seguridad absoluta. Evasiones conocidas, no cubiertas: `grep -r .` y scripts (`node`, `python`) que abren archivos denegados (el deny de Read es "mejor esfuerzo" para Grep y Glob y para `cat`, `head`, `tail`, `sed`, `tee` y redirecciones); rutas absolutas como `/usr/bin/curl`; `sh -c '...'`, `bash -c` y `powershell -Command`; Bash puede modificar archivos aunque falten reglas Edit o Write; opciones globales de Git (`git -C`, `git -c`) y comandos con banderas en otro orden, porque los patrones de argumentos son frágiles; envoltorios como `pnpm exec`. Mitigación: contrato por texto, comprobación Git antes y después de cada delegación y revisión de diff (docs/AGENT_WORKFLOW.md), y revisión humana. PowerShell no figura en `tools` de Develop ni de Testing; las reglas PowerShell protegen la conversación principal.

Los patrones por prefijo son frágiles y no exhaustivos; las ampliaciones de las reglas de borrado y Supabase reducen el riesgo, no lo eliminan. Residuos conocidos, sin regla de deny:
- Bash: agrupaciones de cuatro o más banderas con la r al final (p. ej. `rm -fvIr`), `find ... -delete`, `xargs rm`, `unlink` y envoltorios (`pnpm exec`, `env`, `command`). Un comando de Supabase con `--linked` o `--db-url` en otra posición, salvo los listados.
- PowerShell: `Remove-Item` con `-Recurse` o `-Force` en posición no inicial (`Remove-Item -Path x -Recurse`, `Remove-Item x -Recurse`), `-Recurse:$true` tras otro parámetro, abreviaturas no listadas y llamadas .NET (`[IO.Directory]::Delete`). No se añaden reglas con comodín intermedio porque su soporte en PowerShell no está documentado en los hechos aportados. Esas formas quedan cubiertas solo por el ask genérico `PowerShell(Remove-Item *)` (o por el contrato y la revisión de diff si se usan otros comandos), no por un deny.
- Cobertura PowerShell de las nuevas reglas: la herramienta PowerShell no está disponible para los subagentes, así que no se ha ejecutado ninguna regla PowerShell; su validación efectiva (incluida la sensibilidad a mayúsculas y el comodín final sin espacio) corresponde al Orchestrator o al humano.

## Higiene de Git
`.gitignore` cubre credenciales genéricas, volcados de base de datos y estado local de agentes. `.gitattributes` fija LF. Normalizar los archivos ya rastreados (`git add --renormalize`) requiere autorización humana y no se ha ejecutado.
